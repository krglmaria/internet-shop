# Лабораторная работа №7. Программирование ролевой модели доступа (RBAC)

## Цель работы

Изучить принципы разграничения доступа на основе ролей (Role-Based Access Control, RBAC), спроектировать архитектуру модели «Пользователь — Роль — Разрешение» и реализовать на языке Python программный механизм проверки прав доступа для сценария «Интернет-магазин».

## Описание структуры данных

Программа построена на трёх классах из файла `models.py`.

**Permission (разрешение)** — одно действие над ресурсом. Поля: `name` — уникальный ключ в формате «ресурс:действие» (например, `users:ban`), `description` — описание для человека. Два объекта с одинаковым `name` считаются одним правом (методы `__eq__` и `__hash__`), поэтому права можно хранить в множествах без дубликатов.

**Role (роль)** — должность или функция в системе. Поля: `name` и `permissions` — множество (set) объектов Permission.

**User (пользователь)** — субъект системы. Поля: `username`, `password_hash` (хеш пароля SHA-256, сам пароль не хранится) и `roles` — множество объектов Role. Метод `has_permission(name)` возвращает True, если право есть хотя бы у одной из ролей пользователя.

**Связи многие-ко-многим.** Между пользователями и ролями связь «многие ко многим»: у одного пользователя может быть несколько ролей (например, Менеджер по продажам и Контент-менеджер одновременно), и одна роль может быть назначена многим пользователям. Между ролями и правами связь тоже «многие ко многим»: роль содержит несколько прав, а одно право (например, `catalog:read`) входит в несколько ролей. Прямой связи «пользователь — право» нет: пользователь получает права только через роли.

**Роли и права сценария «Интернет-магазин»:**

| Право | Описание | Клиент | Менеджер по продажам | Контент-менеджер | Администратор |
|---|---|:-:|:-:|:-:|:-:|
| catalog:read | Просмотр каталога | ✓ | ✓ | ✓ | ✓ |
| cart:manage | Корзина и оформление заказа | ✓ | | | |
| orders:process | Обработка заказов | | ✓ | | ✓ |
| products:write | Добавление и редактирование товаров | | | ✓ | ✓ |
| users:ban | Блокировка пользователей | | | | ✓ |

**Модуль `rbac.py`** содержит три функции:

- `load_system(path)` читает `data.json`, проверяет его целостность (нет ли ссылок на несуществующие роли и права, дубликатов, пустых паролей) и при ошибке выдаёт понятное исключение `RBACConfigError`. Пароли при загрузке сразу превращаются в хеши SHA-256.
- `authenticate(users, username, password)` хеширует введённый пароль и сравнивает его с сохранённым хешем; возвращает пользователя или `None`.
- `check_access(user, permission_name)` работает по принципу «запрещено всё, что не разрешено»: возвращает True только если право явно выдано одной из ролей пользователя; для `None` (пользователь не вошёл) и для неизвестных прав возвращает False.

## Ответы на контрольные вопросы

### 1. В чём главное отличие модели RBAC от дискреционного (DAC) и мандатного (MAC) разграничения доступа?

**DAC (дискреционная модель)** — права выдаёт владелец объекта по своему усмотрению. Например, владелец файла сам решает, кому разрешить чтение. Права записываются в матрицу или списки доступа (ACL) «конкретный пользователь — конкретный объект». Это гибко, но при большом числе пользователей становится запутанным, а владелец может случайно раздать лишние права.

**MAC (мандатная модель)** — доступ определяет система, а не владелец. Каждому объекту присваивается уровень секретности (например, «секретно»), каждому пользователю — уровень допуска. Пользователь получает доступ, только если его допуск не ниже уровня объекта. Изменить эти правила обычный пользователь не может. Модель очень надёжная, но жёсткая, применяется в военных и государственных системах.

**RBAC (ролевая модель)** — права привязаны не к пользователю и не к уровню секретности, а к **роли**, то есть к должности в организации. Пользователь получает права, когда ему назначают роль. Главное отличие: доступ определяется тем, *какую работу выполняет человек*, а не тем, кто владелец объекта (DAC) или какой у человека гриф допуска (MAC). Управляет ролями администратор, а не владельцы объектов.

### 2. Почему в RBAC права назначаются именно ролям, а не напрямую пользователям?

1. **Проще управлять.** Ролей мало, а пользователей много. В магазине может быть 10 000 клиентов, но роль «Клиент» одна. Чтобы дать всем клиентам новое право, достаточно изменить одну роль, а не 10 000 записей.
2. **Меньше ошибок.** Новому сотруднику назначают готовую роль, например «Менеджер по продажам», и он сразу получает правильный набор прав. Не нужно вспоминать список прав вручную и рисковать дать лишнее.
3. **Легко отзывать права.** При увольнении или переводе сотрудника достаточно снять или поменять роль — все связанные права исчезнут сразу.
4. **Прозрачность и аудит.** По таблице «роль — права» легко проверить, кто что может. Это соответствует принципу наименьших привилегий: каждая роль содержит только права, нужные для её работы.
5. **Соответствие структуре организации.** Роли повторяют реальные должности, поэтому модель понятна и разработчикам, и руководству.
